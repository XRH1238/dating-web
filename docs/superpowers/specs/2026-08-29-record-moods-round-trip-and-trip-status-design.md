# 出游记录日期、心情、往返路线与顶部行程状态设计

## 背景

当前网站有四个相互关联的体验问题：

1. 填写出游记录时，选完开始日期后仍停留在开始日期，用户还要手动切换到结束日期。
2. “那天的心情”只有五个固定示例，不能写下用户自己的心情。
3. 出游计划的路线编辑器没有明确区分去程和返程，无法直观记录包含多次中转的返程路线。
4. 顶部“下一次出游”在没有当前或未来计划时会回退显示旧计划，让已经结束的旅行仍看起来像下一次出游。

本次设计在不删除旧数据、不改变已完成计划展示范围的前提下，解决以上四个问题。

## 目标

- 开始日期填写完整并通过校验后，自动进入结束日期选择。
- 结束日期不自动填值，即使当天往返也必须由用户再次选择。
- 示例心情继续存在，同时允许添加任意不为空的自定义心情。
- 去程和返程各自拥有清晰的多段路线编辑器，双方都不限制中转次数。
- 顶部行程条准确区分正在出游、未来计划和暂无未来计划。
- 旧计划与旧记录继续兼容，不要求数据迁移或重新填写。

## 非目标

- 不删除、归档或隐藏已完成的出游计划。
- 不改变出游记录的云端表结构。
- 不为自定义心情建立跨记录的全局词库。
- 不限制去程或返程的路线段数量。
- 不在本次工作中重新设计整个计划或记录表单。

## 方案选择

### 往返路线

采用两个独立路线编辑器：一个“去程路线”，一个“返程路线”。两个编辑器都可重复点击“添加一段”，每段填写出发城市、到达城市和交通工具。

路线仍保存到现有 `segments` 数组中，每个新路线段增加方向字段：

```js
{
  from: "杭州",
  to: "上海",
  transport: "高铁",
  direction: "outbound"
}
```

方向只允许：

- `outbound`：去程
- `return`：返程

旧数据没有 `direction` 时按 `outbound` 处理。这样无需新增云端字段，也不会破坏现有计划、地图和缓存数据。

未采用以下方案：

- 去程与返程分别保存为两个数组：结构直观，但会扩大数据兼容与迁移范围。
- 单一路线列表中让每行选择方向：改动较少，但仍不够直观，不能解决用户找不到返程入口的问题。

## 详细交互设计

### 1. 出游记录日期自动切换

日历选择和手动填写都遵循同一规则：

1. 当前编辑目标为开始日期。
2. 开始日期变成完整且有效的 ISO 日期后，保存开始日期。
3. 立即把当前编辑目标切换为结束日期。
4. 结束日期保持空白，不从开始日期复制值。
5. 日历继续显示开始日期所在的年月。
6. 焦点移动到结束日期的“年”输入框；使用日历的用户仍可直接点击同一天或其他日期。

只有从“不完整或无效”变成“完整且有效”时才自动切换，避免用户回头修改开始日期时发生反复跳转。结束日期选择完成后不自动跳到其他表单字段。

结束日期早于开始日期时，继续沿用现有错误提示和校验逻辑。

### 2. 自定义心情

“那天的心情（可多选）”保留现有示例：开心、浪漫、惊喜、治愈、难忘。在示例标签下增加：

- 文本输入框，提示“写下自己的心情”；
- “添加心情”按钮；
- 回车添加能力。

添加规则：

1. 去除首尾空格。
2. 空内容不添加，并在心情区域显示简短提示。
3. 如果内容与已有示例或已添加心情完全相同，直接选中已有标签，不创建重复项。
4. 新心情创建为已选中的复选标签，和示例心情拥有相同外观与取消选择能力。
5. 动态标签使用安全 DOM API 创建，不把用户文字拼入 HTML。

自定义心情只属于当前记录，不写入全局示例列表。它会进入现有 `moods` 数组，因此无需改变出游记录数据结构。

草稿恢复时，如果草稿包含不在示例列表中的心情，先动态创建对应标签，再恢复选中状态。提交成功或清空编辑器时移除动态标签并清空输入框。

### 3. 去程与返程多段路线

计划表单中的“路线分段”替换为两个清晰分组：

- 去程路线
- 返程路线

每组默认显示一行空路线，并分别提供“添加一段”。用户可以添加任意数量的中转段，例如：

```text
去程：杭州 → 上海（高铁）
      上海 → 厦门（飞机）
      厦门 → 鼓浪屿（轮船）

返程：鼓浪屿 → 厦门（轮船）
      厦门 → 武汉（飞机）
      武汉 → 杭州（高铁）
```

空白路线行不会保存；只填写一端城市的行也不会保存，行为与现有路线编辑器一致。每一行仍可单独删除。

计划卡片和地图读取路线时统一规范化方向。旧路线全部视为去程。地图按去程在前、返程在后的顺序绘制。

当去程和返程连接同一对城市时，两条路线使用相反弯曲方向，避免线条和交通图标完全重叠。返程路线不改变交通工具颜色规则。

### 4. 顶部行程状态

顶部行程条不再通过旧计划兜底。每天以本地日期零点为边界，先解析所有有效计划日期，再按以下优先级选择：

1. **正在出游**：`开始日期 <= 今天 <= 结束日期`。如果有多条，选择开始日期最早的一条。
2. **下一次出游**：`开始日期 > 今天`。选择开始日期最近的一条。
3. **暂无下一次出游**：没有正在进行或未来计划。

对应文案：

| 状态 | 顶部标签 | 目的地 | 日期/倒计时 |
| --- | --- | --- | --- |
| 正在出游 | 正在出游 | 当前计划标题 | 显示日期范围，倒计时位置写“旅途中” |
| 未来计划 | 下一次出游 | 最近未来计划标题 | 显示日期范围与“还有 N 天” |
| 无当前/未来计划 | 暂无下一次出游 | 还没有新的计划 | “尚未确定”，天数为 `--`，提示“写下下一次出发” |

无效日期的计划不参与顶部状态选择，但仍保留在计划列表中供用户查看或删除。已完成计划继续显示在计划列表和地图中。

## 数据兼容

### 计划

`segments` 继续是数组。新项目增加 `direction`，旧项目缺失时按 `outbound`：

```js
function normalizeSegmentDirection(value) {
  return value === "return" ? "return" : "outbound";
}
```

云端 `love_plans` 现有 JSON 路线字段无需迁移。

### 记录与草稿

记录仍使用 `moods: string[]`。自定义心情与示例心情没有数据层差异。

草稿仍使用已有本机存储结构；恢复逻辑扩展为动态重建未知心情标签，不更换存储键，不清除旧草稿。

## 错误处理与边界

- 开始日期不完整或非法时不切换到结束日期。
- 开始日期完成后只自动切换一次；回头编辑仍允许重新激活开始日期。
- 当天往返时，结束日期必须由用户再次点击同一天或手动填写同一天。
- 自定义心情仅包含空格时不添加。
- 重复心情不创建第二个标签。
- 路线分组可以有多行，不设置硬上限。
- 只有出发城市和到达城市都存在的路线段才保存。
- 没有当前或未来计划时，顶部不得读取任何已结束计划。
- 多个未来计划按开始日期升序选择；多个正在进行计划按开始日期升序选择。

## 测试策略

### 日期

- 日历选择有效开始日期后，活动目标变成结束日期。
- 手动填完有效开始日期后，活动目标变成结束日期。
- 自动切换后结束日期仍为空。
- 不完整或非法开始日期不会触发切换。
- 当天往返可以再次选择同一天作为结束日期。

### 心情

- 页面包含自定义心情输入和添加按钮。
- 添加自定义心情会创建并选中复选标签。
- 回车可以添加心情且不会提交整个记录表单。
- 空心情被拒绝，重复心情只选中已有标签。
- 自定义心情进入记录的 `moods` 数组。
- 草稿恢复可以重建并选中自定义心情。
- 清空记录编辑器会移除动态心情。

### 路线

- 表单同时存在去程和返程编辑器。
- 两个编辑器都能添加多段路线，不设置数量上限。
- 保存后每段拥有正确的 `direction`。
- 旧路线没有方向时规范化为 `outbound`。
- 去程与返程路线都进入地图数据。
- 同一城市对的往返路线使用不同弧线方向。

### 顶部行程状态

- 正在进行的计划优先于未来计划，并显示“正在出游”。
- 没有进行中计划时选择最近的未来计划。
- 全部计划已结束时显示空状态，不回退到旧计划。
- 无效日期计划不参与选择。
- 已结束计划仍保留在计划列表和地图中。

### 回归验证

- 运行全部 Node 测试。
- 在内置浏览器中分别验证桌面端和移动端表单。
- 实际操作日历与手动日期输入两条路径。
- 实际添加自定义心情并刷新，确认草稿恢复。
- 实际添加包含两次中转的去程与返程并检查地图。
- 用已结束、正在进行和未来三组计划检查顶部行程条。

## 验收标准

- 用户选完开始日期后无需再手动切换到结束日期。
- 系统不会替用户填写结束日期。
- 用户可以添加、取消选择、保存和恢复自定义心情。
- 去程和返程都可以记录两次或更多中转。
- 旧计划无需修改即可继续显示。
- 顶部行程条不会把已结束计划称为“下一次出游”。
- 全部自动化测试通过，桌面端和移动端无横向溢出或控制台错误。
